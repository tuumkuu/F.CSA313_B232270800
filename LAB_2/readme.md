## Алхам 1-2. k6 суулгах болон эхний тест ажиллуулах (BASELINE)

Эхний туршилтаар `script.js` файлыг ашиглан 5 Virtual User (VU)-тэй, 30 секундын хугацаатай тест ажиллуулсан. Тохиргоог script файлын options хэсэгт тодорхойлсон.

Туршилтын үр дүн:

| Үзүүлэлт | Хэмжилтийн утга |
|---|---:|
| Average latency | 146.59 ms |
| p90 latency | 233.49 ms |
| **p95 latency** | **235.1 ms** |
| Нийт HTTP хүсэлт | 230 |
| Throughput | 7.42 req/s |
| Алдааны хувь | 0.00% |

Энэхүү эхний туршилтын p95 үзүүлэлтийг 235.1 ms гэж тодорхойлсон бөгөөд дараагийн алхамд SLO босго тогтооход суурь хэмжилт болгон ашиглав.

Бүтэн үр дүн: `results/run-baseline.txt`

## Алхам 3. Ачааллыг нэмэгдүүлж throughput болон latency-г харьцуулах

Энэ хэсэгт хэрэглэгчдийн тоо нэмэгдэхэд системийн хариу өгөх хугацаа болон хүсэлт боловсруулах хурд хэрхэн өөрчлөгдөхийг судалсан.

`script.js` файлыг stages тохиргоогүйгээр ажиллуулж, 5, 30 болон 100 VU гэсэн гурван өөр ачааллын түвшинд тус бүр нэг минутын турш туршилт хийв.

Ашигласан команд:

```bash
k6 run --vus N --duration 1m script.js
```

Туршилтын харьцуулсан үр дүн:

| VU | p90 | p95 | Throughput | Error rate | Нийт хүсэлт |
|---|---:|---:|---:|---:|---:|
| 5 | 233.61 ms | 235.57 ms | 7.59 req/s | 0.00% | 460 |
| 30 | 231.90 ms | 233.31 ms | 45.43 req/s | 0.00% | 2760 |
| 100 | 231.71 ms | 234.02 ms | 151.68 req/s | 0.00% | 9200 |

Мөн `stages.js` файлыг ашиглан хэрэглэгчдийн тоог 5-аас 30, цаашлаад 100 хүртэл нэмэгдүүлж, эцэст нь 0 болгох ramp тест хийсэн. Ингэснээр ачаалал нэмэгдэх болон буурах үеийн системийн ерөнхий төлөвийг ажигласан.

**Ажиглалт:**

Туршилтын үр дүнгээс харахад хэрэглэгчдийн тоог 5-аас 100 хүртэл нэмэгдүүлэхэд p95 latency бараг өөрчлөгдөөгүй. Энэ үзүүлэлт 233–236 ms орчимд тогтвортой байв.

Харин throughput нь 7.59 req/s-ээс 151.68 req/s хүртэл өссөн. Өөрөөр хэлбэл, хэрэглэгчдийн тоо нэмэгдэхэд систем илүү олон хүсэлт боловсруулж байсан ч хариу өгөх хугацаанд мэдэгдэхүйц удаашрал ажиглагдаагүй.

Энэхүү туршилтаар 100 VU хүртэл системийн гүйцэтгэлд ноцтой сөрөг өөрчлөлт гарах цэг илрээгүй.

## Алхам 4. Threshold ашиглан SLO шалгах

Энэ алхамд системийн гүйцэтгэлд тавих шаардлагыг k6-ийн threshold тохиргоогоор шалгасан.

**SLO босго тодорхойлсон үндэслэл:**

Эхний туршилтын BASELINE p95 latency нь 235.1 ms байсан. Үүнийг 1.5 дахин нэмэгдүүлж тооцоход:

235.1 × 1.5 = 352.65 ms

Иймээс SLO-ийн p95 хязгаарыг 350 ms байхаар сонгосон.

Мөн HTTP хүсэлтийн алдааны хувь 1%-иас бага байх шаардлага тавьсан.

### 4.1 PASS туршилт

`thresholds.js` файлд дараах тохиргоог оруулсан.

```javascript
thresholds: {
  http_req_duration: ['p(95)<350'],
  http_req_failed: ['rate<0.01'],
}
```

30 VU болон 1 минутын хугацаатай ажиллуулахад дараах үр дүн гарсан.

```text
✓ 'p(95)<350' p(95)=233.45ms
✓ 'rate<0.01' rate=0.00%
```

**Үр дүн: PASS**

Хоёр threshold шаардлагыг хангаж, системийн гүйцэтгэл тогтоосон SLO хэмжээнд багтаж байгааг харуулсан.

### 4.2 FAIL туршилт

Дараагийн туршилтаар threshold-ийн утгыг зориудаар хэт бага буюу 50 ms болгон өөрчилсөн.

```javascript
thresholds: {
  http_req_duration: ['p(95)<50'],
}
```

Туршилтын гаралт:

```text
✗ 'p(95)<50' p(95)=231.66ms
time="2026-09-15T21:28:12+08:00" level=error msg="thresholds on metrics 'http_req_duration' have been crossed"
```

**Үр дүн: FAIL**

Бодит p95 latency нь 231.66 ms байсан тул 50 ms гэсэн хатуу шаардлагыг хангаж чадаагүй. Үүний улмаас k6 тестийг алдаатай гэж тэмдэглэж, non-zero exit code-оор дуусгасан.

Энэ нь CI/CD pipeline-д threshold ашиглан системийн чанарыг автоматаар шалгаж, шаардлага хангаагүй build-ийг цааш үргэлжлүүлэхгүй байх боломжтойг харуулж байна.

## Дүгнэлт

Энэхүү лабораторийн ажлаар k6 хэрэгслийг ашиглан веб системийн гүйцэтгэлийг хэд хэдэн ачааллын түвшинд туршиж, latency, throughput болон error rate үзүүлэлтүүдийг хэмжлээ.

Туршилтын явцад хэрэглэгчдийн тоог 5-аас 100 VU хүртэл өсгөхөд p95 latency 235 ms орчимд тогтвортой байсан бол throughput 7.59 req/s-ээс 151.68 req/s хүртэл нэмэгдсэн. Мөн бүх туршилтын үед алдааны хувь 0% байв.

Үүнээс харахад `test.k6.io` сервер нь энэхүү туршилтын ачааллын хүрээнд тогтвортой ажиллаж, хүсэлтийн тоо нэмэгдсэн ч хариу өгөх хугацаа мэдэгдэхүйц удаашраагүй байна.

Гэхдээ энэ үр дүн нь бүх төрлийн систем ижил гүйцэтгэлтэй байна гэсэн үг биш юм. `test.k6.io` нь CDN дээр байрлах хөнгөн демо сайт учраас 100 VU ачаалал түүний хүчин чадлын хязгаарт хүрээгүй байж болно. Илүү их боловсруулалт шаарддаг backend систем дээр ижил туршилт хийхэд latency нэмэгдэх боломжтой.

SLO шалгах хэсэгт p95 latency-г 350 ms-ээс бага, HTTP алдааны хувийг 1%-иас бага байхаар тохируулсан бөгөөд PASS туршилтаар хоёр шаардлага хоёулаа биелсэн. Харин p95 latency-г 50 ms-ээс бага байхаар зориудаар хатуу тогтоосон FAIL туршилтаар k6 шаардлага хангаагүйг автоматаар илрүүлсэн.

Ингэснээр k6 нь зөвхөн системийн хурдыг хэмжихээс гадна тодорхойлсон гүйцэтгэлийн шаардлагыг автоматаар шалгах, CI/CD орчинд чанарын хяналт хийхэд ашиглаж болохыг практик дээр ойлгож авлаа.
